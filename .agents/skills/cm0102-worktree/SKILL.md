# CM 01/02 worktree recovery

Use the current Git worktree as the worker and `F:/src/cm0102-decompiled` as the designated coordinator. The coordinator owns the game, evidence, claims, failure history and acceptance ledger. Workers need no game installation or ledger. Read the coordinator's `AGENTS.md`, `docs/agent/WORKTREES.md` and `docs/agent/C.md`; their fidelity and acceptance rules apply. The existing lane covers accepted lifted functions without accepted C, at most 600 inventory body bytes. Route larger functions or machine batches to the coordinator's normal workflow.

1. Resolve the current worktree with `git rev-parse --show-toplevel`. If it is the coordinator, nested inside the coordinator, or not a separate worktree sharing its Git common directory, stop and explain what is needed. Do not create a worktree unless the user asks. Verify the coordinator has a completed green parent preflight, current required validation and no active writer job. If no parent session exists, start one in the coordinator with `py -3.13 scripts/cmre_session.py start`; coordinate concurrent starts through its existing lease and wait for the same live process. Workers inherit the receipt; they do not start separate sessions or repeat full revalidation. Use `py -3.13` for Python.
2. From the coordinator, run `py -3.13 -m cmre worktree bootstrap WORKER`. Existing valid bindings are reused. For a fresh unbound worker with older tooling, add `--align`: bootstrap checks all destinations before copying exact coordinator tooling/header bytes. Follow `WORKTREES.md` for conflicts, stale bindings, active writers or failed pins; preserve locks, bindings, claims and evidence.
3. Select the user-specified eligible function or inspect `py -3.13 -m cmre next --c --max-bytes 600 -n 20` at the coordinator, respecting any assigned shard or subsystem. Run `cmre screen fn_X` before dispatch and follow `WORKTREES.md` for no-return holds and review obligations. Use a unique owner per session. Claim one function with `py -3.13 -m cmre worktree claim WORKER fn_X --owner OWNER --seconds 3600` at the coordinator. Selection is not a claim: if a competing worker wins, select another eligible function. Do not use `next --claim` before `worktree claim`; the latter creates the coordinated task and claim. Do not take over an existing live claim.
4. Read the worker's ignored `CM0102/Analysis/cmre/worktree/fn_X/packet.json`. Translate the original instructions into only `recovery/c/fn_X.c` in the worker, preserving widths, ABI, operation order, state and bugs. Keep imports and callees as explicit boundaries; do not invent missing behavior. Run `py -3.13 -m cmre worktree test fn_X` from the worker. The coordinator retains attempts and executes the differential gate. Follow `WORKTREES.md` for failures, lease expiry, interruption, and the five-attempt ceiling.
5. On a passing submission, report the function, worker path, source/report hashes, and evidence to the coordinator for independent review. Only the coordinator records review and runs `cmre worktree publish`; a passing test is not acceptance. Continue with another distinct claim only when authorized by the user's task and the preceding function is handed off. Stop with a specific WIP reason if the protocol cannot establish a faithful result. Never push or publish externally.
